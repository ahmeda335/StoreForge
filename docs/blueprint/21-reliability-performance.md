# 21 — Reliability and 22 — Performance

## Patterns: what problem they solve and when not to use them

| Pattern | Problem | Use | Don't use |
|---|---|---|---|
| **Timeout** | A slow dependency holds threads/connections forever, so failures cascade | Every network call (DB statement timeout, HTTP client connect/read, Redis) | Never omit. The default "infinite" is the bug |
| **Retry** | Transient failures (blip, deadlock, 503) | Idempotent operations, with a budget (max attempts, total deadline) | Non-idempotent calls without idempotency keys; on 4xx; in multiple layers at once (retries multiply: 3×3×3 = 27) |
| **Exponential backoff + jitter** | Retrying immediately overloads a recovering dependency (thundering herd) | All retries | — |
| **Circuit breaker** (Resilience4j) | Calling a dead dependency wastes time/threads and delays failure | High-volume sync calls to one dependency (Redis cache, payment provider create, per-webhook-endpoint) | Low-volume calls (not enough data to trip), DB (if the DB is down, nothing works anyway; readiness handles it) |
| **Bulkhead** | One slow dependency/tenant consumes all threads/connections | Separate executors per job queue; per-store concurrency caps for webhooks; api vs. worker processes | Everywhere by default: it adds tuning burden |
| **Fallback** | Degrade instead of fail | Cache miss → DB; recommendations unavailable → empty list | Correctness-critical paths: no "fallback" stock value, no "assume paid" |
| **Idempotency** | Retries and duplicates cause double effects | Every write that can be retried by a client, worker, or provider | — |

## Dependency failure analysis

| Dependency down | What happens | What must not happen | Recovery |
|---|---|---|---|
| **PostgreSQL** | API returns 503 quickly (pool `connectionTimeout` 2–5s); readiness DOWN → LB stops routing; liveness stays UP (no restart storm); workers pause polling with backoff | Hanging requests for 30s+; data corruption; partial orders (TX atomicity prevents it) | Pool reconnects automatically; readiness UP; outbox/jobs resume where they left off |
| **Redis** | Rate limiter falls back to in-memory per instance (approximate); product cache misses → DB; circuit breaker opens to avoid timeout costs | Auth bypass; checkout failing because the cache is down | Circuit half-opens, recovers; cache refills lazily |
| **Payment provider** | Checkout completion returns "payment temporarily unavailable" (503 + Retry-After) **after** the order is created, or before creating it (decision: create payment after order commit; order stays PENDING_PAYMENT; customer retries the payment step with the same idempotency key); circuit breaker trips on sustained failures | Double charges (idempotency keys); orders marked paid without confirmation; stock held forever (expiry job releases) | Reconciliation job; customer retries; webhooks catch up |
| **Email provider** | Email jobs fail and retry with backoff; nothing user-facing blocks | Registration/checkout failing because email is down | Jobs drain when the provider returns; DEAD after N → admin requeue |
| **Message broker** (when introduced) | Outbox accumulates in PG (the outbox *is* the buffer); relay retries | Lost events; HTTP failing | Relay drains backlog in order; alert on outbox age |
| **Webhook destination** | Deliveries retry with backoff up to 72h; subscription paused after sustained failure; per-endpoint isolation | Dispatcher threads all stuck on one slow merchant | Merchant fixes endpoint → replay |

## Performance: measure first, optimize second

1. **Define the question** ("checkout p95 is 900ms at 50 rps; target 400ms").
2. **Baseline** with a reproducible k6 scenario + fixed dataset (e.g. 1k stores, 100k products, 1M orders generated by a seed tool).
3. **Locate** using traces (which span dominates?), DB stats (`pg_stat_statements`: top total-time queries), Hikari pending, JVM profiler (**async-profiler** / JFR flame graphs for CPU and allocation).
4. **Hypothesize** one cause, change **one** thing, and re-run the same scenario.
5. **Record** the result in `docs/testing/load-results/` including failures (negative results teach too).

## Likely bottlenecks and how to see them

| Bottleneck | Symptom | Tool | Typical fix |
|---|---|---|---|
| Missing index | Seq scans, high DB CPU | `EXPLAIN (ANALYZE, BUFFERS)`, `pg_stat_statements` | Composite index matching `WHERE store_id=… ORDER BY created_at` |
| N+1 queries | Trace shows 50 identical SELECT spans | Traces; Hibernate statistics in tests (assert query count) | Fetch joins / batch fetching / DTO projections |
| Large result sets | Memory spikes, slow serialization | Heap profiling, response size | Keyset pagination; projections |
| Connection pool exhaustion | `hikaricp_connections_pending`, timeouts | Hikari metrics | Shorter transactions; no remote calls inside TX; right-size pool |
| Lock contention | Latency under concurrency; `pg_locks`, `lock_timeout` errors | `pg_stat_activity` wait events | Narrower locks, conditional updates, ordering |
| Serialization | CPU in Jackson in flame graph | async-profiler | Smaller DTOs, avoid serializing entities |
| External calls | Long client spans | Traces | Timeouts, async (outbox), caching tokens |
| Cache misses | Low hit ratio, DB load | Cache metrics | TTL tuning, warmup, key design |
